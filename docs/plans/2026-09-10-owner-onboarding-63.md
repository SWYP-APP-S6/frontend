## 구현 순서

1. **모듈과 진입 계약**
   - `:feature:owner:onboarding`을 생성하고 Android library/Compose convention plugin을 적용한다.
   - 기존 Version Catalog와 `:core:designsystem`을 사용한다. 새로운 공통 기반 클래스나 전체 Data 구조를 선행 구축하지 않는다.
   - `settings.gradle.kts` 등록과 프로젝트 지도 갱신, 필요한 Owner 전용 의존성 조립을 수행한다.
   - 입력 상태, 사용자 입력 처리, 뒤로가기·주소 검색·신청 완료의 외부 전달을 구분한다. 최상위 로그인/홈 분기는 #56에서 조립한다.
   - 홈 브랜치와 충돌할 `settings.gradle.kts`, `app/build.gradle.kts`, Owner MainScreen, 프로젝트 지도는 병합 시 양쪽 모듈 등록을 유지한다. 개발용 진입은 Debug에 한정하고 Release에서 임의로 등록 화면을 강제하지 않는다.
2. **입력 상태와 검증**
   - 한 등록 흐름에서 상호, 가게 종류, 우편번호, 기본·상세 주소, 연락처, 영업 시간, 영업 요일을 소유한다.
   - Step1→Step2→Step1 이동 및 구성 변경에서 입력을 보존한다. 기존 TextFieldState API와 중복 문자열 상태를 불필요하게 병행하지 않는다.
   - 필수값 충족 여부로 다음/등록 신청 버튼을 제어한다. 공백 상호, 미선택 종류·주소, 연락처 형식, 요일 미선택을 검증한다.
   - 상세 주소 필수 여부, 연락처 허용 형식, 심야·24시간 영업 규칙은 아래 확인 항목에 따라 확정한다.
3. **Step1 UI**
   - Owner 타이포그래피와 기존 `MangroInputBox`, `MangroTextField`, `MangroDropdownField`, `MangroButton`, TopAppBar를 재사용한다.
   - 필드 제목의 Figma 크기와 기존 InputBox 스타일 차이를 확인하고 필요한 최소 확장 또는 기존 하위 컴포넌트 조합을 사용한다.
   - 가게 종류는 목록 열기→선택→닫기까지 구현한다. 예시 문구를 실제 입력값으로 저장하지 않는다.
   - 주소 검색 선택 결과로 우편번호와 기본 주소를 반영하고 상세 주소를 입력받는다. 검색 취소 시 기존 값을 유지한다.
4. **Step2 UI**
   - 연락처 입력 키보드와 표시 형식, 공개 안내를 구현한다.
   - 시작·종료 시간 선택과 일~토 다중 선택을 구현한다. 초기값은 디자인 예시를 근거로 실제 정책으로 확정하지 않는다.
   - 시간은 내부적으로 일관된 값으로 보관하고 표시 형식과 분리한다.
5. **신청 처리 및 외부 연결**
   - 유효한 두 단계 입력 전체를 신청 요청으로 구성한다.
   - 전송 중 중복 클릭 방지, 실패 시 입력 유지·재시도, 성공 시 완료 이벤트를 처리한다.
   - API 계약이 없으면 UI 테스트용 가짜 구현과 실제 연결 지점을 구분한다. 가짜 성공으로 실서비스 신청 완료를 처리하지 않는다.
   - 심사 대기 또는 홈 이동은 사업 정책과 응답 상태가 확정된 뒤 #56의 앱 진입 분기와 연결한다.
6. **화면 품질과 검증**
   - 원본 전화·경고 아이콘을 확인하고 기존 동일 도형을 재사용하거나 실제 Figma asset을 로컬 리소스로 변환한다.
   - 상태 바·내비게이션 바는 OS inset으로 처리한다. 입력 폼은 스크롤 가능하게 하고 IME와 하단 CTA가 마지막 필드를 가리지 않게 한다.
   - 360dp 기준 화면, 320dp 작은 화면, 큰 글꼴, 키보드 표시, 뒤로가기, 상태 복원을 확인한다.
